# Lacewing Analytics property screening

Screen one property in England for a long-term rental investment, or save an area-and-budget enquiry for manual follow-up. A local Python server gathers property evidence, calculates returns and generates a ten-page investment PDF, a one-page Sources & Evidence PDF and a one-page Internal review PDF. The cover heading and photograph placeholders are template text. Nearby amenities and transport are an explicit cited-research topic; an administrative ward alone does not establish them. Supplied accommodation details and matched PropertyData floor area retain separate source labels. The frontend uses plain HTML, CSS and JavaScript. Records are stored as JSON files; there is no database. The public form sends JSON brief text by email through Un-static; save that text as a JSON file to import it into the local dashboard.

## Run locally

Python 3.9.6 is compatible with the application. From the cloned project directory on macOS or Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit `.env` to add your PropertyData key. Install the [Codex CLI](https://developers.openai.com/codex/cli/) and run `codex login` with your ChatGPT account, then start the server:

```bash
python app.py
```

Open [the analyst dashboard](http://127.0.0.1:8000). The existing `/review` URL also opens the dashboard. Keep the terminal running; stop with Ctrl+C. For later sessions, activate `.venv` and run `python app.py` again. Change `PORT` in `.env` if port 8000 is already in use.

On Windows, create the environment with `py -m venv .venv` and activate it with `.venv\Scripts\activate` in Command Prompt. The remaining commands are the same, except use `copy .env.example .env`.

Open `web/public/index.html#contact` in your browser (or open the landing page and select Enquire) to preview the public brief and download it as JSON. The form markup, styles and script are embedded in this single public website file. Online submissions use Un-static and work when the page is served over HTTP(S), including the local preview below. The public form does not connect to the local dashboard.

To import a brief, copy the JSON text from the notification email's message field into a UTF-8 plain-text file named `investor-brief.json`. Copy only the JSON object, from its opening `{` through its closing `}`, without the email's headings or footer. Click **+** beside **Client submissions** in the local dashboard and choose that file or a file from the form's **Download brief as JSON** button. The dashboard validates and opens it as a new submission, using the same input check and report workflow as a direct form submission. Area enquiries remain available for manual follow-up. Invalid files show an alert.

## API configuration

For the full workflow, configure PropertyData and sign into Codex on the same machine/account that runs the Python server. The integration was verified with Codex CLI 0.165.0. Codex is the only AI provider; the app has no direct AI API clients or provider-selection setting.

| Provider | API key setting | Optional model setting |
| --- | --- | --- |
| PropertyData | `PROPERTYDATA_API_KEY` | — |
| Codex app-server | Existing `codex login` with ChatGPT | `CODEX_MODEL` (blank uses Codex's configured default) |

Codex handles intake checks, corrections, research, commentary and report edits. It launches a local app-server and uses your existing ChatGPT subscription allowance. API-key authentication is rejected and there is no paid AI API fallback. Subscription usage limits still apply; Firecrawl has its own allowance. `CODEX_BIN` can specify the CLI path when it is not on the server's PATH. `CODEX_REASONING_EFFORT` defaults to `medium`. Restart the server after changing `.env`. The form, dashboard and reports use Lacewing Analytics branding; the dashboard title remains Property Screening. The form, dashboard and reports share the landing page’s deep green, gold and ivory palette, wing mark, Cormorant Garamond headings and Inter text. Fonts are bundled locally in `web/assets/fonts` with their licences, so the interface and PDFs work without font downloads. Existing saved PDFs pick up the styling when regenerated.

Research and AI edit planning enable only Firecrawl's `firecrawl_search` and `firecrawl_scrape` through `https://mcp.firecrawl.dev/v2/mcp`. Existing MCP authentication can be reused; alternatively set `FIRECRAWL_API_KEY`. Personal skills, plugins, other MCP servers, built-in web search, shell, browser and image tools are disabled in dashboard tasks. Intake and commentary writing have no web tools. The dashboard does not inherit the skills used in your interactive Codex session. Your personal Codex configuration is not changed.

Research works in short rounds, preserving completed findings and tool evidence between rounds. Missing amenities/transport context receives the first lookup. Concrete follow-ups, such as a newer linked fee schedule, stay on a checklist until an observed search or page read marks them checked or unavailable; a checked task still needs validated evidence before it can establish a fact. Research targets five minutes (`CODEX_RESEARCH_TARGET_SECONDS=300`) and has a ten-minute ceiling (`CODEX_RESEARCH_MAX_SECONDS=600`, capped at 600). Pending tasks can continue past the target or two quiet rounds; without them, research stops when useful leads are exhausted or progress stalls. Actual Firecrawl usage limits stop research with a distinct `limited` audit status; timeouts and the hard deadline retain unfinished tasks as a partial failure. Both preserve accepted findings and permit another attempt on a later generation instead of caching the run as completed. Retries of the same supplied request retain pending tasks and checked history, and reopen lookups blocked by a usage limit; changing the request or provider snapshot starts a fresh checklist. This budget covers research, separately from PropertyData gathering and report writing. Existing PDFs remain in place if generation fails.

Missing purchase price or rent can use a labelled Codex estimate and uncertainty range supported by at least two distinct, dated, cited comparisons. Imperfect bedroom/size matches can support an explained adjustment; a five-bedroom provider limit does not become a five-bedroom subject assumption. Per-room rents cannot become whole-house estimates. Supplied prices/rents take precedence. Existing PropertyData valuations and strict matched medians keep their precedence too. Estimates are stored separately from provider results and inputs, expire after 30 days, and become unusable when property details or their supporting evidence change. The report, Sources and Internal review templates are unchanged.

Without PropertyData, generation still attempts public research and can use a manually supplied rent. Live reports require Codex with a ChatGPT login. Writing failures stop generation visibly rather than silently substituting template conclusions. Demo/offline test generation can still use explicitly labelled template text. Failed AI edits keep the previous report.

Keys stay in the backend. AI requests include property information, financial assumptions, calculated results, evidence and analyst notes. Structured contact name/email fields are excluded from intake, correction, research and narrative requests. Intake review is one small text-model call; applying a correction uses a separate text call without another intake review, PropertyData call or web search. Calculations run in Python; the AI researches evidence, proposes labelled estimates, writes commentary and proposes edits.

## Workflow

1. Complete the property brief in the landing page’s enquiry section with property details, buyer circumstances and cash or expected mortgage terms. An unfinished brief survives reloads in the same tab using session storage. Download the JSON brief and import it using **+** beside **Client submissions** in the local dashboard. Alternatively, submit through Un-static, save the emailed JSON text as a `.json` file and import it. One small AI intake review starts on import, before any PropertyData or web research. It reviews the whole brief in context, with no fixed price/yield/area thresholds, and leaves the inputs unchanged. Its concise response appears in the existing message area beneath Additional information for the AI. There is no input-check panel or button.
2. Read the submission check, add any corrections or context to **Additional information for the AI**, then select **Generate report**. Generation waits for an in-progress submission check to finish; its completed findings are advisory. Explicit corrections are interpreted and saved with before/after history before research. The original input check is never rerun on refresh, edits, corrections, generation or regeneration. A failed/interrupted attempt is recorded without a retry, and older submissions are not checked retrospectively. Missing optional fields alone are not mistakes. Generation gathers evidence, calculates results and writes the PDF. If essential financial evidence remains unavailable after research, it keeps the ten-page layout and both one-page companions, preserving independent calculations and marking dependent results unavailable; unsupported returns and bidding figures are withheld, and the report cannot be finalized as a complete financial assessment. Provider/writing failures are shown separately.
3. Review the PDF. Draft-only **Additional information for the AI** controls are hidden once a PDF exists, including an incomplete financial assessment. Generated reports do not reopen the draft controls or display the separate unresolved-evidence banner. Use **Tell the AI what to change** and **Update PDF** for titles, wording, presentation, property facts or financial assumptions. The editor can use Firecrawl to research the requested topic, such as nearby transport or current local fees. New facts use the same citation, quotation and property-identity checks as generation; validated evidence reaches the source register, calculations and commentary. Explicit input values retain precedence. Proposed input corrections receive a separate tools-disabled extraction check (60-second maximum), which sees the request and saved inputs but no new web results; research cannot silently become an analyst-supplied override. Researched property changes invalidate dependent cached valuation/size outputs before recalculation. Ordinary wording/style edits need no searches. Edit planning remains one targeted turn with a 180-second timeout, not a full report investigation; valuation estimates use existing eligible comparison IDs, with newly discovered comparisons available to a subsequent request. Tool failures or unsupported research edits keep the previous report. Accepted research and actual tool calls are recorded in edit history.
4. Upload one **Cover photo** and up to ten **House photos**. Uploads and removals automatically update the PDF. Uploads accept JPEG, PNG or WebP, up to 10 MB per image. Each save checks the latest report revision while retaining the selected files; concurrent photo changes remain protected from overwrite. Photo updates rebuild the existing PDF without calling PropertyData or starting the research pipeline. Drafts show ten additional-photo slots; finalized reports show only uploaded photographs.
5. Click **Approve & finalize** when satisfied. This requires a saved cover photo, saved photo changes and no pending AI instructions. Finalization records the review and downloads the PDF. Later edits reset approval. Send the finished report to the client yourself.

Required form fields carry a red asterisk. Unmarked fields are recommended when known; extra preferences, notes, links and feedback permission are labelled optional. Main goal, floor area, monthly rent and other valuation details can be left blank. Money inputs accept UK-style amounts such as `£250,000` and `£1,520.50`; percentage inputs also accept `%`. Invalid grouping, out-of-range values and fractional pennies are rejected rather than silently changed. Mortgage briefs ask for a deposit in pounds or percent, then interest-only / repayment / not sure. The full loan term appears only for repayment, defaults to 25 years and is required in that form. Interest rate is optional: an omitted rate uses a disclosed 5.5% assumption, with 4%, 5% and 6% comparisons. An optional fixed-rate period of 2, 3, 5 or 10 years changes the projection after expiry, using a supplied reset rate or an explicit two-percentage-point rise scenario. Tracker and unknown choices remain distinct. The full term is separate from the fixed-rate deal and ownership period. Legacy mortgage amounts remain supported. Interest coverage is reported at the model and stress rates; no universal lender pass threshold is assumed.

An area-only enquiry asks for an area and purchase budget, saves the contact details and any goal supplied, and appears as **Needs follow-up**. It does not search for properties, generate a PDF or spend API credits. One optional checkbox permits contact about a feedback call or a testimonial request; it saves both contact preferences separately from the required terms acceptance. This form remains for England long-term rental investments; a separate homebuyer form is deferred. The terms and privacy links open dedicated `#terms` and `#privacy` views within the landing HTML. They contain the supplied documents verbatim, including placeholders, with Markdown headings, bold text and lists rendered as HTML. The standalone form preview points to the same landing-page views. No testimonial publication permission is inferred.

The dashboard reopens the last submission viewed in that browser. The bin icon on a submission deletes its JSON, photos, PDFs and history; deletion is disabled while processing. **Sources/evidence** and **Internal review** sit beside **Export JSON**. The existing PDF viewer, CSV and spreadsheet-image downloads are retained. **Export JSON** downloads the full saved record, including inputs, evidence, calculations, report edits and approval information.

Dashboard saves renew a stale local session token once after a server restart, without reloading the page. **Update PDF** fetches the latest record revision and retries one rejected revision conflict while retaining the typed request. Already-running jobs, repeated conflicts and unrelated failures still stop safely; network failures are not automatically resubmitted. Concurrent photo changes remain protected.

For researched edits, independently quoted amenities/transport findings are combined into the existing locality paragraph with their source references, within its 65-word budget. If citation or estimate validation fails, the editor gets one tools-disabled correction attempt (up to 60 seconds) using only pages already read and existing comparisons. It cannot start another search or bypass validation. A remaining failure keeps the previous report and stores the latest request, rejected response/tool results and feedback in `last_failed_edit` for diagnosis.

## Report contents

The complete investment PDF has exactly ten pages. Compact tables and concise commentary keep the evidence readable without continuation pages:

1. Property introduction: address, cover photograph and three boxes for location/nearby places, accommodation and price with its basis.
2. The complete investment overview, verdict, summary and qualifications, followed by returns and growth projections.
3. Acquisition/financing costs, upfront safety provision, input bases and bidding guidance.
4. Cash-flow spreadsheet image, annual projections and mortgage/reset assumptions.
5. Quantified downside tests, interest-rate comparisons, interest coverage and ownership-period returns.
6. Property facts, environmental/designation risks, licensing status and additional photographs.
7. Subject sale history, local price chart, nearby market activity and best five asking-price comparisons.
8. Best five rental and completed-sale candidates, retaining bedroom/type/size/distance/date differences and rent basis.
9. Yield and cash-flow target results, neutral observations and material risks. Funding requirements are separate information.
10. Itemised operating costs, effective modelling defaults with their bases, and individual/company tax explanation.

Investigative bedroom discrepancies, weak price evidence, incomplete cost research and staff preparation tasks go into the one-page Internal review. Essential assumptions and material financing, licensing, flood and listed-status risks remain in the investor report. Advertising dates are labelled **Observed on**; completed transactions use sale dates. Full house addresses are retained where evidence supplies them; street-only adverts are explicitly marked as lacking house identity. Address links open Google Maps and the original evidence links remain in Sources.

The separate Sources & Evidence PDF is a compact, two-column list of references cited in the report, deduplicated by URL and linked through numbered citations. It excludes research transcripts, excerpts and verbose failure logs; those remain intact in the saved record / JSON export. Both companions are measured to remain exactly one page. An oversized reference list or internal note produces a clear editing error instead of spilling onto extra pages. All artifacts are built in a staging directory and published under fresh filenames only after all three PDFs succeed. Failed edits and regenerations retain the previous record and exports. Excessive report text causes a clear editing error before publishing the PDF; it is never silently cut or pushed onto extra pages. AI writing has explicit word budgets. The full comparison list remains in the saved record and the full monthly schedule is exported as CSV. Both spreadsheet images remain downloadable as PNGs. Fictional records retain their demo watermark after approval.

## Evidence and calculations

New property briefs require the property address, postcode, type and bedroom count, alongside contact details and essential buyer/financing information. Floor area, construction age, condition, bathrooms, outdoor space and parking are recommended but can be unknown. Automated valuations require those details to be available by the time research runs; missing details do not prevent saving the brief. Studios and converted flats use the flat model; bungalows use their detached/semi-detached/terraced attachment. The report flags these broader categories. New-build and confirmed tenure information filter the recorded-sale requests. The property profile runs first and can fill missing size, age, EPC and tenure only when the identity matches; the floor-area lookup can also fill remaining gaps when it finds an unambiguous match. These lookups are not guaranteed to find every field and never overwrite client-supplied facts. House aliases and town formatting differences are accepted only with matching postcode, numbered street and no ambiguous flat/unit identifiers.

A complete successful research run with all core requests eligible, including a selected refurbishment estimate, budgets **30–32 PropertyData credits**, before the additional conditional requests below:

| Request | Credits |
| --- | ---: |
| `property` | 20 |
| `rents`, `prices-per-sqf`, `growth`, `demand` | 4 |
| `valuation-sale`, `valuation-rent` | 2 |
| `demand-rent`, `sold-prices-per-sqf`, `build-cost` | 3 |
| `growth-psf` | 1 |
| **Core requests** | **30** |
| `national-data` (regional rent inflation): fresh download / valid shared cache | 1 / 0 |
| `sold-prices`: broader search needed / sufficient existing comparisons | 1 / 0 |
| **Standard total** | **30–32** |

Regional rental inflation is shared between properties through a local cache in `.research-cache` inside the configured records directory (normally `data/records`, which is gitignored). It expires after 24 hours. A cached response must contain a usable dated observation for the property's verified region; corrupt, expired, future-dated or unusable entries are replaced. Unsuccessful or unusable downloads are not cached, and a failed refresh never silently substitutes expired data. Simultaneous reports in the local app share a single download. Each report retains the original retrieval timestamp, dataset dates and whether its source was cached; cache hits are not included in `paid_requests`. An explicit backend `refresh_evidence: true` also bypasses the shared cache.

The broader `sold-prices` search runs only when the existing evidence contains fewer than three qualifying distinct properties. Qualifying sales must have a positive price and source link, a sale date within the last 18 calendar months (never in the future), known distance greater than zero and no more than one mile, matching type and bedroom count, and known floor area within 75–125% of the subject. Known subject tenure must match, and new-build subjects require new-build sales. The subject itself and repeat sales of the same address do not count. Missing facts do not qualify, so sparse, failed or weak size-filtered results still trigger the broader search. These remain candidates requiring analyst review. The saved `sold_search` decision records the qualifying count and whether the fallback ran.

Additional conditional requests each budget one credit: `prices` when fewer than three type/bedroom/size-compatible asking-price candidates are available; `planning-applications` when refurbishment is planned (ten results, within 0.25 miles, last three years, no decision filter); `floor-areas` and `energy-efficiency` only for gaps remaining after the profile; and `title` only for missing lease years with a single matched leasehold title. At most five such requests are added, so the overall budget is 30–37 credits where all core requests are eligible. Calls are paced to the lowest documented rate limit of twelve per thirty seconds. There is no area-yields request or extra address-match request. The saved evidence lists the requests attempted and their budgeted credits; this is not an account billing receipt. Actual provider billing can be lower for incomplete/no-match responses. Choosing **No refurbishment** hides the budget/finish fields, skips the `build-cost` request and omits its estimate from the report; works costs are zero. Light, moderate or heavy refurbishment requests an estimate when a valid floor area is available. Provider limits still apply: the documented minimum area is 300 sqft for valuations and 600 sqft for refurbishment. Inputs below those limits are not inflated to force a result. Missing or failed estimates are marked unavailable. A refurbishment reference is added to investment costs only when works are planned and no explicit budget was supplied; an explicit budget takes precedence, and contingency is shown separately. Existing saved briefs with a reference level selected retain that choice. The estimate is not a contractor quote. When works are selected, a supplied or supported after-works value takes precedence. Otherwise the explicitly labelled value scenario recovers 50% of the works budget, excluding contingency, allowing for costs that do not increase resale value. This is an editable modelling assumption, not market evidence; it is separate from annual market growth and does not add rent. Unknown works budgets leave dependent totals unavailable.

The app also queries HM Land Registry for transactions and the England House Price Index as background evidence, without PropertyData credits. The report's historical chart uses the local growth series. Listing links remain references; the app does not scrape portals or download their photographs.

Research snapshots are reused and refreshed after sixty days, or when explicitly requested through the backend. When an API key is configured, the next Generate report action upgrades an older research snapshot with a fresh run of the new requests. Photo changes and AI edits do not perform this PropertyData research upgrade. Evidence older than thirty days is flagged. Paid PropertyData requests are not automatically retried. Photo changes and approval reuse saved evidence; report edits may add focused Firecrawl evidence using its separate allowance, without querying PropertyData. Changes to property identity invalidate evidence, and changes to valuation inputs or refurbishment specification discard the affected estimates rather than reuse stale results. Previously generated files remain intact until an explicit update; older report models require Generate report to refresh the evidence and AI conclusions before photo-only changes or finalization.

Monthly rent is selected in this order: explicit supplied rent, analyst-selected rental comparables, property-specific rental valuation, the median of at least three suitably matched researched asking rents, then a clearly provisional area average. Per-room/student adverts are not silently converted to whole-property rents. Supported ranges require distinct, dated comparisons and compatible type, bedrooms and location; sale ranges additionally require known compatible size and tenure. Sparse evidence can inform discussion but does not establish a defensible range. Rental valuations with unknown units are withheld instead of guessing weekly versus monthly. Candidate comparables prefer the same bedroom count, then the closest available counts, followed by type, size, distance, condition and date, and are not silently treated as analyst-verified matches. Property sale history requires matching identity. Asking-price and sold-price-per-square-foot requests use a floor-area band of 75–125% of the known subject area; the actual returned radius remains visible because searches can widen. Individual asking and sold comparisons are retained separately, with observed dates, dimensions, distance, listing age and links where supplied. Rental sample counts, radius and the middle 80% range describe the local sample, not a property valuation confidence interval. Sales/rental demand metrics remain area context and are not converted into vacancy assumptions. Matched council tax and environmental/designation facts are reported with their limits; nearby listed buildings do not establish the subject’s listed status. Council tax is not added again to operating costs, which already include an empty-period bills budget. Planning searches are limited nearby context, not a permission check. Missing fields are not treated as cleared checks.

Property records accept up to twenty bedrooms. PropertyData's `valuation-sale` and `valuation-rent` requests support at most five bedrooms, so the app skips those valuations for larger properties before making a paid call and records the reason. For `rents` and `prices`, it omits the optional bedroom filter instead and labels the result as local data across all bedroom counts, not a matched valuation. The actual property bedroom count is preserved. A supplied monthly rent or analyst-selected rental comparables takes precedence; when broader local rent is used as a fallback, its scope is stated in the report and flagged as provisional.

The purchase price always remains the supplied listing/offer/proposed price when known. If unknown, a sale valuation or the median of sufficiently matched completed sales can supply a clearly labelled provisional purchase scenario. Future sale scenarios start from the property-specific sale valuation when available, otherwise the purchase-price proxy. These two figures are not interchangeable.

The financial model calculates:

- Gross yield: scheduled annual rent divided by purchase price.
- Net yield on cost: stabilised income after vacancy and operating costs divided by acquisition cost, including refurbishment and contingency.
- Cash-on-cash: stabilised cash flow after debt payments, before income tax, divided by cash invested including reserves and upfront finance fees.
- Cash, interest-only or repayment financing using a deposit or a legacy supplied mortgage amount and rate. A not-sure repayment choice is explicitly modelled as interest-only and flagged. Legacy records can still use an explicit LTV assumption.
- Monthly cash flow, annual totals, downside scenarios, break-even rent, exit proceeds and approximate annual IRR for 3, 5 and 10 years of ownership and renting. The CSV contains a separate monthly schedule for each period. Interest-only comparisons beyond the supplied mortgage term are withheld until refinancing terms are known.

Management defaults to 14.4% including VAT for ordinary whole-house letting, or 18% where the existing notes establish an HMO/shared/student letting arrangement. Bedroom count alone and possible conversions do not select the shared strategy. Explicit investor rates are preserved. Safety defaults are illustrative allowances, not quotes: £150 upfront and £250 annually for whole-house letting, or £600 upfront and £500 annually for an established shared arrangement. Annual safety replaces the existing compliance allowance rather than being added to it; upfront safety can be marked as included in refurbishment or other purchase costs to avoid duplication. Existing explicit budgets take precedence. Major remedial works and licence fees remain unpriced unless supplied.

Regular cleaning and cleaning between tenancies are separate landlord-paid annual budgets. Blank means unconfirmed and excluded, not zero cost or included in maintenance. Repair allowances exclude cleaning and planned refurbishment; the report calls out overlap with service charges.

The existing Codex/Firecrawl research rounds also estimate defaulted purchase legal fees, survey fees, local management fees and a property-specific repair allowance. Explicitly supplied costs always take priority. Fee and management estimates require supporting passages from pages actually read, with scope and adjustments recorded in `evidence.cost_estimates`; changed property/transaction scope or evidence older than thirty days invalidates them. Legal budgets include VAT and routine searches/disbursements, excluding separately calculated SDLT and mortgage fees. Surveys identify the proposed RICS level. If evidence is insufficient, legal/survey budgets remain £2,000/£600 and management keeps the disclosed tenancy-dependent default.

Maintenance can use annual scheduled rent (typically newer/leasehold flats) or the initial property valuation/purchase-price proxy (typically older/freehold houses). The analyst explains the rate, property facts and limitations; an allowance based on supplied facts is not a quote or survey. Value-based maintenance increases with cost inflation in later years and stays tied to the same initial value in rent stresses and bidding comparisons. Without a supported estimate, older/freehold houses use a disclosed 1% value fallback where value is available; otherwise the fallback is 5% of scheduled rent. Explicit `maintenance_basis` values `rent`/`value` select the calculation basis; `auto` lets the estimate choose, while an explicitly supplied percentage retains its previous rent meaning unless a basis is also supplied. Unknown required value/rent leaves dependent figures unavailable.

PDF text calls these analyst estimates. The writer must cover five consistent risk topics: financing, occupancy/permissions, cost assumptions, excluded costs/taxes and environmental/designation uncertainty. Material risk paragraphs remain in the client report even when they also request verification. The existing ten-page investment report and one-page Sources and Internal review layouts are retained; saved reports change only on regeneration.

AI research runs before calculations using Codex and Firecrawl. Search results lead to full-page reads; supported findings need observed source URLs and verbatim supporting passages. Subject facts need an exact identity match, and designation conclusions need official sources. Research never overwrites explicit client facts. Dates, scope, tool results, searches and unresolved gaps are saved in `evidence.research`; cited references appear in the compact companion PDF. Search failures are distinguished from inconclusive results and retried on a later generation; completed research is reused for up to 30 days unless explicitly refreshed. Public evidence cannot necessarily establish private lease terms, actual cleaning frequency, achieved rents or contractor quotes.

AI writes numerical, source-cited conclusions about purchasing, rents, growth and stress results. Figures must occur in the supplied evidence/calculation packet, and supplied/default targets remain distinct. Cash required, available cash and any shortfall are funding information, not PASS/FAIL targets. The deterministic model computes yield/cash-flow price ceilings including SDLT and financing; it never rescales a fixed mortgage silently to make a bid work.

When no price-growth assumption is supplied, the model uses the annualised local historical change over at least two years as an explicitly labelled scenario. It does not claim to predict future growth. The sold-price-per-square-foot history cross-check compares annualised changes over common periods; opposite directions or a difference of at least two percentage points are flagged, and the rates are never averaged. It can supply an explicitly labelled fallback scenario when the main growth series is absent. Rent growth uses the latest dated annual rental-inflation observation for the verified English region from `national-data`, unless explicitly supplied. The basis distinguishes an observation date from a dataset publication date. Regional history is extrapolated as a scenario, not a forecast of this property’s future rent. Unmatched, ambiguous, stale (over eighteen months), future-dated or implausible observations are withheld; missing evidence produces a visible no-growth fallback and warning. An intentionally supplied zero is preserved. Income and disposal taxes are not automatically assessed; adviser-supplied budgets can be included. An absent income-tax budget appears as a dash in the spreadsheet and blank in the CSV, not as a zero tax liability. Buyer ownership/residency affects SDLT; not owning another property is not treated as automatic first-time-buyer relief for a rental purchase. England purchase-tax settings and their source dates live in `config/tax_rules.json` and require maintenance. The ownership-specific explanation in `screening/tax_notes.py` cites GOV.UK guidance checked on 29 October 2026; it identifies taxes excluded from the model. Defaults and missing evidence remain identified in the report. AI edits cannot directly overwrite computed results.

Open `web/public/index.html` directly to preview the marketing website. The `web/public/` folder contains only this public HTML file for upload. It retains its embedded images; `web/assets/logo.png` is the supplied logo for reuse. The website includes the client brief in its enquiry section (`#contact`), with inline form styles and JavaScript. The local app serves `web/index.html` at `/` and `/review`. Edit the form markup in `#property-brief` within `web/public/index.html`; keep `web/assets/intake.js` and the embedded `#property-brief-script` in sync when changing the form script.

Each submission folder contains `record.json`, prior revisions in `history/`, uploaded photos and generated PDF/PNG/CSV files. Writes use atomic JSON replacement and process-local locks. Run a single local server process; this app is not configured as a hosted multi-user service.

`.gitignore` excludes `.env` and its variants, local credentials, `data/`, virtual environments, Python caches and editor files. Only the blank `.env.example` belongs in the repository. API keys and saved submissions are therefore not included when cloning: configure a new `.env` and copy `data/` separately if you want existing records. Back up `data/` before moving machines.

Run the offline regression suite with `python3 -m unittest discover -s tests -q`. Run the dashboard import and photo-upload checks with `node --test tests/review_import.test.cjs tests/review_photos.test.cjs`; these use Node's built-in test runner and mocked requests. PDF checks use the installed Poppler commands (`pdfinfo`, `pdftotext`, `pdftohtml`, `pdfimages`); no paid report runs are needed. Existing saved files remain unchanged until a successful update. An older model needs an AI Update PDF to recalculate and refresh numerical commentary; photo-only updates must not silently retain stale financial wording.
